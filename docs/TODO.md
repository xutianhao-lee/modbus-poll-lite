## ✅ P0 —— 缺陷修复（已完成）

- [x] **15/16 功能码写多线圈/多寄存器会发出畸形请求**
      改为"写模式"：选中 05/06/15/16 时窗口不进行轮询，提示行显示蓝色写模式说明；
      新增 `功能` 菜单四项写入 + `write_multiple_registers()` / `write_multiple_coils()`。
- [x] **别名列无法编辑**
      双击「别名」列 → 输入框；右键行 → 上下文菜单（设置别名 / 写入 / 复制本行）。
- [x] **广播（从站号 0）语义不正确**
      unit == 0 时发送后立即返回，不等待应答。从站侧同步改为"执行但不应答"（符合规范）。
- [x] **写入后未立即刷新**
      新增 `_read_once()`，写入完成后立即读取并刷新，不等待下一轮询周期。

### 2026-09-22 第 7 批（游标改为屏幕固定）
> 反馈：实测后要求「游标要固定」——第一版采用锚定时间戳方案，运行中会随波形向左漂移。

| 项 | 验证结果 |
|---|---|
| **运行中游标不漂移** | 0.6s + 5 次刷新后，比例仍是 0.2995、像素 319→319 ✔ |
| 拖动（存屏幕比例而非时间戳） | 拖到 30%/90%，像素误差 < 2 ✔ |
| ΔT 语义变更 | 现在 = 窗口时长 × 屏距比例，是定值 ✔ |
| 读数语义 | 取游标当前位置**下方**最接近的样本 ✔ |
| 越界标记 | 游标在数据范围外 → 显示 `—` 且 inside=False ✔ |

> **设计取舍**：屏幕固定 vs 时间戳锚定。
> 锚定时间戳可"标记特定事件点"，但滚动时游标位置会偏移；屏幕固定则位置稳定、
> 可实时读取数值，更符合伺服调试后台示波器的使用习惯。**最终选用屏幕固定方案。**

### 2026-09-22 第 9 批（曲线的流畅度）
> 反馈：「采样点有点少，波形有点卡」。经分析为两个独立原因。

| 原因 | 处理 |
|---|---|
| **滚动卡顿**——重绘周期 250ms，滚动呈跳跃状 | 改为 **80ms（≈12fps）** |
| **采样点少**——采样密度 = 1÷扫描周期，1000ms 时每秒仅 1 点 | 工具栏新增**「采样周期」下拉**（50~2000ms），可直接修改数据区，无需打开 F8；状态栏显示「N 点/秒」，低于 5 点/秒时黄色告警 |

| 项 | 验证结果 |
|---|---|
| 重绘耗时（10 路 × 900 点） | **4.8 ms/次**，预算 80ms，余量 16 倍 ✔ |
| 重绘耗时（20 路 × 900 点，极端） | 9.2 ms/次 ✔ |
| 抽稀上限改为**按画布宽度**计算 | 窗口放大时不会拖慢重绘 ✔ |
| 稀疏时标出真实采样点 | 60 点 → 图元 +60 ✔ |
| 密集时自动抽稀 | 1200 点 → 图元反而更少 ✔ |
| 采样周期下拉 ↔ 数据区双向同步 | ✔ |

> 经验：**采样密度受 Modbus 轮询周期限制，曲线本身无法产生更多数据点**。
> 串口场景不可一味调小周期——9600 波特率下单帧传输需数十毫秒，发送过快将导致大量超时。

### 2026-09-22 第 14 批（补上 SerialTransport 的测试）

> 起因：验证本地测试能否覆盖串口。排查发现 `SerialTransport`

|---|---|
| `SerialTransport` 改用 `serial_for_url` | 传 `COM3` 行为不变；支持 pyserial 的 URL 形式，其中 `loop://` 可用于回环测试、`socket://` 可将 TCP 连接当串口使用 |
| 新增 `read_available(timeout)` | Test Center「原始字节」模式需要——接收字节数事先未知，不能像 `read_exact` 那样固定等待指定字节数 |
| 测试第 5 节 | 使用 `loop://` 验证打开/写入/读取/关闭 |

| 项 | 验证结果 |
|---|---|
| `SerialTransport` 打开 loop:// | 参数（19200-8E1）被接受 ✔ |
| sendall → read_exact 回环一致 | `01 03 80 00 00 0A EC 0D` 原样收回 ✔ |
| read_available / read_until | ✔ |
| close | ✔ |
| 回归总数 | 52 + 90 + **45** = **187 项** 全绿 ✔ |

**当前串口覆盖状况**：

| 层 | 覆盖 | 方式 |
|---|---|---|
| 帧格式（CRC/LRC/分帧/异常帧） | ✅ | RTU/ASCII over TCP 端到端 22 项 |
| `SerialTransport` 调用 pyserial | ✅ **本批补上** | loop:// 回环 |
| **Windows 串口驱动收发** | ❌ | 需要真实硬件或虚拟串口对（com0com） |

> 补充最后一层覆盖需要：**com0com 虚拟串口对**（建立一对 COM 端口，主站与从站各连一个）
> 或**真实硬件**（USB 转串口线 TX-RX 短接构成回环）。
> 另注：从站模拟器目前仅支持 TCP，用于串口测试前需先为其增加串口收发功能。

## ⏳ 待有硬件后验证：串口驱动层

**验证串口的 Windows 驱动层**——目前唯一未覆盖的环节。

现状：帧格式（CRC/LRC/帧分割）与 `SerialTransport` 调用 pyserial 均已测试，
唯独 **pyserial 实际打开 COM 口收发**的环节未经真实设备验证。
在验证之前，串口功能属于"理论可行、未经现场检验"状态。

获得 **USB 转串口线**后，可选择任一方案：

### 方案 A——单线回环（最简便）

```
1. 用一根杜邦线把转换器的 TX 和 RX 短接（DB9 是 2 脚和 3 脚）
2. 确认设备管理器里的 COM 号
3. 运行：
     # 在项目根目录执行
     PYTHONIOENCODING=utf-8 python tests/test_modbus_serial.py
4. 查看【5】节——当前使用 loop://，改为真实 COM 口后重新执行
```

能够正常收发即说明驱动层工作正常。

### 方案 B——com0com 虚拟串口对（无需额外硬件）

```
1. 安装 com0com，建立一对 COM10 <-> COM11
2. 从站跑 COM10、主站连 COM11
   （⚠ 从站目前仅支持 TCP，需先增加串口收发功能，约 30 行代码）
```

### 方案 C——双线对接，主站与从站直接通信

同样需要先为从站增加串口支持。
**另有附带用途**：使用 USB-485 线缆，将其作为从站测试 PLC 的主站程序。
